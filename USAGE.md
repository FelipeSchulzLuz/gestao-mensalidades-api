# Project quick usage

This file is a short onboarding guide for developers and CI operators. It consolidates the most common commands and explains how to use `scripts/toolbox.sh`, secrets, and the recommended local dev flow.

## Quick start (development)

1. Copy environment template and edit values locally (never commit `.env`):

```bash
cp .env.docker.example .env.docker
cp .env.docker .env
# Edit .env with REAL values (DB host, ports, secrets)
# NEVER commit .env or .env.docker to Git!
```

2. Make scripts executable (once):

```bash
chmod +x scripts/*.sh
```

3. Start infra and app (recommended wrapper):

```bash
# Recommended: uses the wrapper that invokes Makefile and runs Flyway
./scripts/run-make.sh start
```

Or, with the toolbox helper:

```bash
./scripts/toolbox.sh start-with-flyway
```

4. Tail app logs:

```bash
docker compose logs -f app
```

## `scripts/toolbox.sh` (central helper)

Run `./scripts/toolbox.sh` with one of the subcommands below:

- `secrets:prompt` — interactive prompt to set missing GitHub Actions secrets (uses GitHub CLI `gh`).
- `secrets:import` — scans `.env.docker`, `.env` and docs to suggest secrets to add; asks confirmation before setting them via `gh`.
- `db:apply-migration` — run Flyway migrations via docker-compose/Makefile.
- `db:recreate` — destructive: recreate the development DB (use with caution).
- `start-with-flyway` — copy `.env.docker` to `.env` (if missing), ensure infra is up and run Flyway before starting app.

Examples:

```bash
./scripts/toolbox.sh secrets:import
./scripts/toolbox.sh secrets:prompt
./scripts/toolbox.sh db:apply-migration
```

### Requirements

- `gh` (GitHub CLI) installed and authenticated for secrets automation.
- `docker` and `docker compose` for local infra commands.

## Secrets required by CI

Add these secrets in the repository (Settings → Secrets & variables → Actions) or use `./scripts/toolbox.sh secrets:prompt`:

- `DOCKER_USERNAME` and `DOCKER_PASSWORD` — for publishing images to Docker Hub/GHCR.
- `DOCKER_REGISTRY` — e.g. `docker.io` or `ghcr.io` (can be set in `.env` instead of secret for public registries).
- `SONAR_TOKEN` — optional, SonarCloud token for analysis.
- `SECURITY_UPLOAD_TOKEN` — fallback PAT for SARIF/security uploads (Fine-grained PAT with `Security events: Write`).
- `NVD_API_KEY` — optional, reduces 403 risk for OWASP dependency-check.

## CI notes

- The pipeline needs `security-events: write` permission for SARIF upload; if your org restricts the `GITHUB_TOKEN`, create a Fine-grained PAT and store it in `SECURITY_UPLOAD_TOKEN`.
- If `dependency-check` fails with NVD 403, consider setting `NVD_API_KEY` or making the step non-fatal in the workflow.

## Troubleshooting

- If the toolbox tries to use `gh` and it's missing, install it and authenticate:

```bash
# Debian/Ubuntu example (server):
curl -fsSL https://cli.github.com/packages/githubcli-archive-keyring.gpg | sudo dd of=/usr/share/keyrings/githubcli-archive-keyring.gpg
sudo chmod go+r /usr/share/keyrings/githubcli-archive-keyring.gpg
sudo apt-add-repository "deb [arch=$(dpkg --print-architecture) signed-by=/usr/share/keyrings/githubcli-archive-keyring.gpg] https://cli.github.com/packages stable main"
sudo apt update
sudo apt install gh

# then authenticate:
gh auth login
```

- To manually set a secret (instead of using `gh`):

  1. Go to the repo on GitHub → Settings → Secrets & variables → Actions → New repository secret
  2. Add `NAME` and `VALUE`
